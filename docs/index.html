SlintPlot: native charts for Slint in Rust

SlintPlot draws charts with Slint's own Path, Rectangle and Text elements. They are not images: charts stay sharp at any scale, follow the theme and dark mode, and react to the mouse.

Cartesian charts

Line, bar, horizontal bar, scatter and bubble charts; stacked, mixed, stepped and filled variants.

Radial charts

Pie, doughnut, polar area, radar and radial bar charts.

Time and heatmaps

Time series with date axes, candlestick and OHLC charts, Gantt charts, matrix heatmaps, matrix charts of sized circles and GitHub-style calendar heatmaps.

Hierarchies and business

Treemaps, sunbursts, funnels, waterfalls, dumbbells, gauges and bullet charts.

Interactive

Tooltips, hover highlights, clickable legends, click callbacks, zoom and pan, keyboard navigation.

Large datasets

Min-max decimation and on-demand data reading for millions of points.

Getting started

1. Add the dependencies

SlintPlot is used both as a regular dependency (the register! macro) and as a build dependency (to find its .slint files).

[dependencies]
slint = "1.18"
slintplot = "0.3"

[build-dependencies]
slint-build = "1.18"
slintplot = "0.3"

2. Make the library importable: build.rs

fn main() {
    let config = slint_build::CompilerConfiguration::new().with_library_paths(
        std::collections::HashMap::from([("slintplot".into(), slintplot::library_path())]),
    );
    slint_build::compile_with_config("ui/app.slint", config).unwrap();
}

3. Use a chart: ui/app.slint

import { ChartEngine, LineChart } from "@slintplot";
export { ChartEngine } // required, so Rust can connect it

export component App inherits Window {
    preferred-width: 800px;
    preferred-height: 500px;

    // Only the data and the properties that differ from their default.
    // The LineChart section lists every property.
    LineChart {
        title: "Revenue";
        labels: ["Jan", "Feb", "Mar", "Apr", "May", "Jun"];
        datasets: [
            { label: "2025", values: [12, 19, 8, 15, 22, 18], fill: true, tension: 0.4 },
            { label: "2026", values: [15, 22, 13, 24, 26, 30], tension: 0.4 },
        ];
    }
}

Import only the charts you use, plus ChartEngine, which must always be imported and exported. Charts you don't import cost nothing: Slint generates code only for the components your UI uses. register! connects the whole engine either way.

4. Connect the engine: src/main.rs

slint::include_modules!();

fn main() -> Result<(), slint::PlatformError> {
    let app = App::new()?;
    slintplot::register!(app);
    app.run()
}
Software renderer: to draw lines, areas and pies with Slint's software renderer, enable Slint's software-renderer-path feature: slint = { version = "1.18", features = ["software-renderer-path"] }.

How it works

Charts are Slint components. Geometry such as line paths, bar positions and axis ticks is computed in Rust by the ChartEngine global's pure callbacks, which slintplot::register! connects. Because the callbacks are pure, Slint recomputes them automatically when the chart's size, data or theme changes.

  • Data is a Slint model. Set it in .slint or from Rust; changing a row updates the chart.
  • Colors are optional. Datasets and slices without a color take the next color of the active theme.
  • Two requirements: export ChartEngine from your root .slint file, and call slintplot::register! once after creating the component.

RadialBarChart

One ring per bar, the first outermost, each filled along its arc in proportion to its value over a faint gray track, like activity rings and radial progress bars. A full ring is max-value, or the largest value when it is 0; larger values fill the ring. The rings cover sweep degrees (270 by default) clockwise from start-angle, and each label goes in the opening before the start of its ring. Each value is written just past the end of its bar, or inside the bar when it is nearly full. The bars take the theme's colors in turn, or one color for all; a bar's own color overrides both. They grow in when the chart appears and move to new values when a bar's value changes; change the bars' rows in place (set_row_data) rather than replacing the model, so that each bar keeps its ring. Hovering a ring or its label shows its value. The bars are ChartSlices, as in a pie chart, so the same data can be shown both ways.

CandlestickChart

Prices over a time axis: for each period, a body from the open to the close, green when the price rose and red when it fell, and a wick from the low to the high. With ohlc: true, each period is a bar from the low to the high with a tick to the left at the open and one to the right at the close. x is the number of seconds after time-origin, ticks fall on round times, and the chart zooms and pans like TimeSeriesChart. The value axis fits the candles in view.

By default the candles sit side by side, skipping the gaps between them such as nights, weekends and holidays; the ticks are at the candles where their dates fall. With skip-gaps: false, the time axis is linear and gaps stay empty.

When there are more candles than room for them, they are merged: the first open, the highest high, the lowest low and the last close, and the tooltip shows the dates they span. On a linear time axis they are merged into hours, days, weeks (from Monday), months, quarters or years in local time; with skip-gaps, into a few candles each, counted from the first. A merged candle at the edge always holds all its candles, so its values don't change while panning, and zooming in shows the single candles again.

show-volume adds a strip of volume bars below the candles, on their own scale; show-last-price draws a dashed line at the last close, labeled on the value axis. Axes and formatting

Cartesian charts and HorizontalBarChart share these axis options:

  • Titles: x-title below the x axis, y-title above the y axis.

A second value axis

Datasets with right-axis: true are plotted against a second value axis on the right, for two measures of different size or unit in one chart. Each axis shows while a visible dataset uses it, as with Chart.js' display: 'auto': hide the right-axis datasets from the legend and the right axis goes, and the plot widens; hide the left ones and the grid follows the right axis. The right axis has its own settings: y2-title, y2-value-prefix, y2-value-suffix, y2-value-decimals, y2-fixed-range with y2-min-value and y2-max-value, y2-logarithmic and y2-begin-at-zero. Tooltips and data labels write each value in its own axis' format, and stacked datasets stack on their own axis.

The right axis gets as many ticks as the left one, at steps such as 15 or 40, so its ticks sit on the left axis' grid lines. When either axis is fixed or logarithmic they can't line up; then the right axis chooses its own ticks, without grid lines. It works in LineChart, BarChart, ScatterChart, BubbleChart and TimeSeriesChart; other charts ignore right-axis.

BarChart {

Interaction

  • Tooltips and highlights. Line, bar and radar charts show every dataset's value for the category under the mouse. Scatter and bubble charts show the nearest point, pies the slice under the mouse, and treemaps and sunbursts the item under the mouse with its share of the total. Updating data from Rust

Datasets and slices are ordinary Slint models. Use a VecModel and change rows; the chart updates on its own.

use std::rc::Rc;
use slint::{Model, ModelRc, VecModel};

slint::include_modules!();

fn main() -> Result<(), slint::PlatformError> {
    let app = App::new()?;
    slintplot::register!(app);

    let values = Rc::new(VecModel::from(vec![3.0, 7.0, 4.0]));
    let datasets = Rc::new(VecModel::from(vec![ChartDataset {
        label: "Sales".into(),
        values: values.clone().into(),
        tension: 0.4,
        ..Default::default()
    }]));
    app.set_datasets(datasets.clone().into());

    // Later: append a value, or replace a row.
    values.push(9.0);
    if let Some(mut ds) = datasets.row_data(0) {
        ds.fill = true;
        datasets.set_row_data(0, ds);
    }
    app.run()
}

Here App declares in-out property <[ChartDataset]> datasets; and passes it to a chart with datasets <=> root.datasets;. The generated Rust types (ChartDataset, ChartXY, ChartSlice, ...) come from slint::include_modules!().

Streaming

For live data, give a dataset a model that appends new values and drops the oldest. Charts read their models on demand and follow the model's change notifications, so an update costs one frame, not a copy of the data. VecModel works for small windows, but remove(0) moves every remaining value. For large windows, use a ring buffer, like the StreamModel in the example apps (stream_model.rs, about 70 lines):

/// The latest `capacity` values of a stream.
pub struct StreamModel<T> {
    values: RefCell<VecDeque<T>>,
    capacity: usize,
    notify: ModelNotify,
}

impl<T: Clone + 'static> StreamModel<T> {
    /// Appends values, dropping the oldest ones beyond the capacity.
    pub fn extend(&self, new: impl IntoIterator<Item = T>) {
        let mut values = self.values.borrow_mut();
        let before = values.len();
        values.extend(new);
        let added = values.len() - before;
        let dropped = values.len().saturating_sub(self.capacity);
        values.drain(..dropped);
        let len = values.len();
        drop(values);
        if added == 0 {
            return;
        }
        if dropped >= before {
            self.notify.reset();
        } else {
            if dropped > 0 {
                self.notify.row_removed(0, dropped);
            }
            self.notify.row_added(len - added, added);
        }
    }
}

impl<T: Clone + 'static> Model for StreamModel<T> {
    type Data = T;
    fn row_count(&self) -> usize { self.values.borrow().len() }
    fn row_data(&self, row: usize) -> Option<T> { self.values.borrow().get(row).cloned() }
    fn model_tracker(&self) -> &dyn ModelTracker { &self.notify }
}

// A time series dataset of the latest 10,000 points:
let points = Rc::new(StreamModel::new(10_000, Vec::new()));
datasets.push(ChartDataset { points: points.clone().into(), ..Default::default() });
// Later, from a timer:
points.extend(new_points);
  • Batch the samples. Data can arrive far faster than a screen refreshes. Collect the samples that arrived since the last frame and add them with one extend per frame, from a slint::Timer of about 16 ms; the stress app streams 100,000 samples a second this way.
  • Keep time series in time order. TimeSeriesChart finds the visible points with a binary search, so each dataset's points must be sorted by x. Appending newer points keeps them sorted. Scatter and bubble charts take points in any order.
  • Let the x axis move. In line and bar charts, stream the labels along with the values (another StreamModel), so the categories move with the data. Time series axes follow the points' times on their own.
  • Mind the window size. How many values a chart can show and still update at 60 frames per second depends on the chart and the machine; see streaming limits.

The gallery's Live data sample streams a time series at 10 to 60 updates a second, and the stress app streams up to 8 datasets at up to 100,000 samples a second, with windows from 1,000 values to everything it has received.

Memory stays level however long the app runs: a StreamModel holds at most its capacity, and the charts keep nothing between frames that grows with time. The fuzz app's soak test renders the same data over and over, with hovering, clicks, scrolling and keys, and checks that memory in use stops growing. In 10 minutes, 7,760 rounds of all 18 chart components, it went from 870 KB after the first rounds to 874 KB at the end.

Data from other threads

Slint models live on the UI thread: a VecModel or StreamModel can't be sent to another thread, and changing one from elsewhere doesn't compile. Read the data on any thread or async task, send it to the UI thread, and change the models there. Two ways:

  • A stream of samples (a serial port, a socket, a sensor): send them through a channel, and move what arrived into the model once a frame, from a slint::Timer. This also batches the samples, as Streaming recommends.
  • An occasional result (a database query, a file): pass a closure to the UI thread with upgrade_in_event_loop on the component's weak handle, or slint::invoke_from_event_loop.
use std::rc::Rc;
use std::sync::mpsc;
use std::time::Duration;
use slint::{Timer, TimerMode, VecModel};

// A thread, or a tokio task, reads the samples and sends them on.
let (tx, rx) = mpsc::channel::<f32>();
std::thread::spawn(move || loop {
    let sample = read_sensor();
    if tx.send(sample).is_err() {
        break; // The app has closed.
    }
});

// On the UI thread, once a frame: move what arrived into the model.
let values = Rc::new(StreamModel::new(10_000, Vec::new()));
let timer = Timer::default();
timer.start(TimerMode::Repeated, Duration::from_millis(16), {
    let values = values.clone();
    move || values.extend(rx.try_iter())
});

// A one-off result: build the models on the UI thread.
let weak = app.as_weak();
std::thread::spawn(move || {
    let rows: Vec<f32> = fetch_rows();
    weak.upgrade_in_event_loop(move |app| {
        let values = Rc::new(VecModel::from(rows));
        // ... put `values` in a ChartDataset and set it on `app`.
    })
    .ok();
});

Keep the Timer alive as long as the chart updates: dropping it stops it. With tokio, use tokio::sync::mpsc and its try_recv in the same way, or call upgrade_in_event_loop from the task; Slint's event loop runs on the main thread, so run tokio on its own threads.

Large datasets

  • Turn off point markers with show-points: false. Each marker is an element.
  • Keep decimation on (decimate: true, the default). A line with more than twice as many points as pixels is drawn as one span per pixel column, which looks the same and draws far faster: about 240 ms instead of 16 s for 3 lines of 1,000,000 points in the software renderer.
  • Zoom in. Values are read from the models on demand, so a zoomed-in chart reads only the visible values, and changes outside the view cause no work.

How decimation works

Line charts, time series and scatter charts with show-lines: true decimate a line when it has more than twice as many points as the plot is wide in pixels. Within each pixel column, the line becomes one vertical span from the lowest to the highest point in the column, joined to the previous column. In line charts, a filled area keeps the first, lowest, highest and last point of each column.

  • Peaks are kept. The lowest and highest value of every column are always drawn, so a single spike among a million points still shows. What is lost is detail inside a column: two values a pixel apart look like one span.
  • Lines are straight. tension and stepped don't apply while a line is decimated, and point markers aren't drawn. Zoom in until there are fewer than two points per pixel, and the line is drawn as usual again.
  • The points must be in x order. Decimation groups neighbouring points by pixel column; SlintPlot doesn't sort them. Line and bar charts are always in order, since the x axis is the index. For time series, points must be sorted by time anyway (see Streaming): out of order, points can be missing from the view, and the line jumps back and forth. A scatter chart with lines joins the points in data order, decimated or not, so sort them by x first if the line should go left to right.
  • Only what is shown is decimated. The data in your models isn't changed. Tooltips and hovered-index report the real values.

assert_eq!((scale.min, scale.max, scale.step), (0.0, 100.0, 20.0));
let labels: Vec<String> = scale.ticks().iter().map(|&v| format_tick(v, scale.step)).collect();
// ["0", "20", "40", "60", "80", "100"]

ChartEngine

ChartEngine is the Slint global that the chart components call to compute their geometry. You don't call it yourself, but it has to be exported from your root .slint file so that register! can connect it. Its pure callbacks include layout, value-axis, pie-layout, radar-layout, treemap-layout, sunburst-layout, funnel-layout, waterfall-layout, dumbbell-layout, gantt-layout, gauge-layout, bullet-layout, candle-layout, radial-bar-layout, matrix-layout, the hit tests and format-value. moving-average(candles, period) is for you: the simple moving average of the closes, as points for a line over a CandlestickChart; in Rust, slintplot::candle::moving_average computes the same.

Performance

SlintPlot draws every chart with Slint's own elements: a path per line, a rectangle per bar, a text per label. That keeps charts sharp, themeable and interactive, but every element costs drawing time, and that cost grows with the data. The stress test app, slintplot-stress, was built to find where it starts to matter: it pushes each chart type from 100 to 1,000,000 points, streams new data at 60 Hz, and shows the layout and frame times live. Use it to check what's fast enough for your app before you build it; we use it to catch slowdowns in SlintPlot before a release.

How it's measured

The numbers below come from slintplot-stress --bench, which renders each configuration without a window:

  • Machine: Apple M4 (10 cores, 16 GB), macOS 27, a release build of SlintPlot 0.2.0 with Slint 1.18.
  • Renderer: Slint's software renderer, on one CPU core, into a 1280×800 pixel buffer.
  • Data: three datasets (three groups for the sunburst), random walks.
  • Frame: the chart's layout plus drawing every pixel, measured once per configuration. Showing it on a screen isn't included. Hover is the next frame after the mouse moves over the chart.
  • Runs: each number is the median of three runs. Most numbers differed between runs by ±3% or less; the fastest frames, around 1–6 ms, by up to ±21%.

At 60 frames per second, a frame has 16.7 ms. Frames below that can be animated and streamed smoothly; slower ones are fine for charts that change now and then.

Streaming limits

How much data can a chart show while it streams, and still update at 60 or 30 frames per second? slintplot-stress --bench-stream measures it: each update appends one value to each of three datasets, drops the oldest, and renders a full frame. It grows the window (the values kept per dataset) in 1-2-5 steps from 1,000 to 10,000,000, and times each size: the 95th percentile of up to 100 updates, the median of three runs. Same machine and renderer as above: Apple M4, macOS 27, Slint's software renderer on one core, 1280×800.

  • Zoomed in, the data size doesn't matter. A view of the latest 1,000 values updates in about 7 ms with 1,000 values kept per dataset or with 10,000,000: the chart finds the visible values with a binary search and reads only those.
  • Showing everything, decimation sets the limit. A decimated line updates at 60 fps with 50,000 values per dataset, and takes 130–150 ms with 500,000. Below about 2,500 values (twice the plot width in pixels) lines aren't decimated, so up to there all line charts cost the same.
  • Scatter charts read every point, since their points can be in any order, so even zoomed in they slow down from about 20,000 points per dataset.
  • One value per update. At higher data rates, the samples that arrive between frames are added in one batch per frame (see Streaming). The benchmark doesn't measure those larger batches; the stress app shows their effect live, at up to 100,000 samples a second.

What the numbers mean

  • Up to about 1,000 points per dataset, every chart fits in a 60 fps frame, except the sunburst (21 ms).
  • Lines of any size stay usable with decimation, which is on by default: 5 ms at 10,000 points, 24 ms at 100,000 and about 240 ms at 1,000,000 for a full redraw. Hovering stays at about 3 ms at every size, and zooming in to 0.1% of a million points brings a frame to 46 ms. Without decimation, a million-point line takes 16 s to draw.
  • Bars, scatter markers and the one-shape-per-item charts grow with the count. For animation and streaming, keep them to about 1,000 bars, markers or items; at 10,000 a frame takes 27–265 ms.
  • Up to 10,000 points, drawing takes most of the time. Computing the chart takes 1–7 ms (19 ms for a line with point markers) of frames of 5–265 ms. With decimated million-point lines it's the other way round: reading and decimating the data takes 186 ms of the 237 ms frame.

What isn't measured

  • GPU renderers. Desktop apps use Slint's FemtoVG or Skia renderer by default, which draw on the graphics card. They haven't been benchmarked; expect different, usually faster, drawing.
  • The browser. The web gallery runs SlintPlot as WebAssembly; it isn't benchmarked, and is likely slower.
  • Other machines. Everything above is from one fast computer. Older or low-power hardware is slower; embedded devices are untested.
  • Memory use and start-up time.

To measure your own machine, run the benchmark, or open the app to try the charts with live numbers:

cargo install slintplot-stress
slintplot-stress --bench          # the tables above, for your machine
slintplot-stress --bench-stream   # only the streaming limits, with your machine's specs
slintplot-stress                  # the interactive stress test

Limitations

What SlintPlot 0.3 doesn't do yet, or does with restrictions:

  • Rust only. The chart geometry is computed in Rust and connected with register!, so the library can't be used from Slint's C++, JavaScript or Python APIs. For the same reason, charts aren't drawn in Slint's live preview or SlintPad.
  • Platforms. Tested on desktop (macOS, Windows and Linux) and in the browser with WebAssembly, from version 0.1.2: the gallery runs in the browser. Embedded (MCU) builds are untested. With Slint's software renderer, enable its software-renderer-path feature, or charts aren't drawn.
  • 14 built-in languages. ChartTheme.language covers 14 languages; for others, set the ChartLocale fields yourself. Grouping is always in thousands (no Indian lakh grouping, and four-digit numbers are grouped in every language), digits are Western, and right-to-left layout isn't supported.
  • Time zones. Time axes are in UTC, with an optional fixed offset. Named time zones and daylight saving time changes aren't supported.
  • Two value axes at most, and only in line, bar, scatter, bubble and time series charts: horizontal bar charts have one value axis.
  • Zoom, pan and decimation work in the cartesian charts only (line, bar, scatter and time series), and in candlestick and Gantt charts along time. Zoom is off by default.
  • Eight colors per theme. With more than eight datasets the colors repeat. Set your own palette for more (see Theming).
  • Large charts of separate shapes are slower. Sunburst, waterfall, dumbbell and funnel charts draw every item as its own shape: about 270 ms for a sunburst with 10,000 items, and about 80–100 ms for waterfall and dumbbell charts. With up to 1,000 items, a frame takes under 30 ms. Decimation applies to lines only.
  • Label fitting is estimated. Sunburst and treemap labels are kept or hidden from an estimate of the text width, so very wide or narrow fonts can be clipped or hidden too early.
  • No image or PDF export. To save a chart as PNG, render the window with Slint's software renderer, as the gallery's --snapshot option does.
  • Sunburst data order. A parent item must come before its children in items.
  • Requirements. Slint 1.18 or later and Rust 1.88 or later.
